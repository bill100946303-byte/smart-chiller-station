# UI_POLISH_BOUNDARY_CURRENT

## 1. 目的

本文用于明确当前稳定维护阶段，已签收页面可以做哪些 UI 美化，以及哪些内容不得借“美化”名义扩项。

适用前提：

- 当前项目处于一期迁移基本完成后的稳定维护阶段
- `/trend-analysis` 已完成回归并正式签收
- 当前不进入新能力开发，不进入新页面迁移

## 2. 事项归类

- 类型：已签收维护项
- 当前动作建议：`maintain`

## 3. 当前结论

当前可以做 UI 美化，但只能做：

- polish
- 收边
- 提质
- 一致性修正

当前不能做：

- 新功能开发
- 新页面开发
- 重做信息架构
- 借视觉优化扩大一期范围

## 4. 允许开展的 UI 美化

### 4.1 视觉统一

允许：

- 卡片圆角、边框、阴影统一
- 页面间距、区块间距统一
- 状态色、强调色一致化
- 图标尺寸与对齐统一

### 4.2 字体与层级优化

允许：

- 标题、副标题、卡片数值层级优化
- 描述文案和辅助文案的权重优化
- 减少工程态、增强产品感

### 4.3 导航与顶部状态优化

允许：

- 左侧导航 hover / active 样式优化
- 顶栏信息密度优化
- `sourceStatus` / `freshness` 展示更清晰

### 4.4 空态 / degraded / stale 态优化

允许：

- 状态文案布局优化
- 图文层级优化
- 降级态和正常态的区分增强

说明：

- 只能优化表达，不新增状态逻辑

### 4.5 已签收页的小幅 polish

优先可做页面：

- `/dashboard`
- `/login`
- `/alarms`
- `/devices`
- `/system-overview`
- `/scene-control`

目标：

- 让已签收页面更统一、更稳定、更适合长期展示

## 5. 当前不建议开展的 UI 改动

### 5.1 不建议碰的页面

- `/optimize-demo`
  - 当前只是治理态 demo，不值得重做视觉
- `/projects`
  - 当前属于项目切换治理入口，不应伪装成单纯视觉 polish 项

### 5.2 不允许做的事情

禁止：

- 改页面主流程
- 改页面核心信息结构
- 改接口依赖
- 因美化新增字段或新接口
- 将 demo 页包装成正式业务页
- 让美化工作影响已签收结论

## 6. 当前推荐顺序

若要做 UI 美化，建议按这个顺序：

1. `/dashboard`
2. `/devices`
3. `/system-overview`
4. `/scene-control`
5. `/alarms`
6. `/login`

说明：

- 先收用户最常见入口页
- 再收中枢业务页
- 最后收辅助入口

## 7. 当前边界判断

### 可以做

- 视觉 polish
- 统一样式
- 状态表达优化
- 已签收页观感提质

### 不应该做

- 借机开启第二轮大开发
- 借机把治理态入口扩成新工作台
- 借机给 demo 页升格

## 8. 一句话结论

当前 UI 美化可以做，但只能按“已签收页面视觉收边”执行，不得演变成新一轮范围扩张。
