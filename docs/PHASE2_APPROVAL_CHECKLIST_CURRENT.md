## 1. 目的

本文用于给当前主仓库进入 Phase 2 前提供一页审批清单，避免在一期维护态封版后重新滑回无边界扩项。

- 一期迁移主线已完成维护态封版
- 核心页面已正式签收：
  - `/login`
  - `/dashboard`
  - `/system-overview`

  - `/trend-analysis`

  - `frontend.3001`

## 3. Phase 2 开工门

只有同时满足以下条件，才允许进入 Phase 2 开工评审：

### 3.1 已完成明确批准

必须有明确拍板，不允许默认开工。

审批结果至少要明确：

- 是否进入 Phase 2
- 先开哪一条线
- 谁负责主控

### 3.2 一次只开一条主线

Phase 2 不允许并发启动多条主线。

当前候选只能四选一：

- `2D/3D` 深交互增强
- `/simulate` 治理预留
- `/assistant/query` 治理预留
- 正式 optimize engine 评审

### 3.3 必须先写边界

在任何实现前，必须先固定：

- 目标
- 不做项
- 是否进主合同
- 是否新增页面
- 是否只做治理不做实现
- 验收口径

### 3.4 必须指定责任归属

至少明确：

- 主控负责人
- BFF 负责人
- UI 负责人
- 文档/签收负责人

## 4. 当前默认结论

在没有明确批准前，当前默认状态仍然是：

- `maintain`
- `monitor`
- `backlog-only`

也就是说：

- 不启动 `simulate`
- 不启动 `assistant`
- 不启动正式 optimize engine
- 不新增主业务域
- 不恢复大规模页面迁移

## 5. 推荐审批顺序

如果确需进入 Phase 2，建议按这个顺序评审：

1. 趋势历史问题复盘是否已归档完毕
2. 是否继续冻结 `/optimize-demo` 为治理态
3. 是否优先做 `2D/3D` 深交互增强
4. 是否有必要开启 `/simulate` 治理预留
5. 是否明确推迟 `/assistant/query` 与正式 optimize engine

## 6. 审批通过后的最小动作

审批通过后，第一步不是直接写代码，而是：

1. 固定本次只开的一条主线
2. 新增对应任务包
3. 明确“不做项”
4. 明确签收标准
5. 再进入实施

## 7. 当前结论

当前项目已经具备进入 Phase 2 审批的条件，
但还不具备“默认自动开工”的条件。

一句话：

- **Phase 2 可以评审**
- **Phase 2 不能默认启动**
