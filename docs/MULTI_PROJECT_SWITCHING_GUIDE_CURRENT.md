# MULTI_PROJECT_SWITCHING_GUIDE_CURRENT

## 1. 目的

本文用于说明当前阶段如果要管理多个项目、多个冷站站点，应该如何切换与治理。

适用前提：

- 当前主仓库仍处于稳定维护阶段
- 不新增新能力主线
- 不重构当前 `shell / bff / legacy adapter` 边界

本文是治理建议，不是开发任务单。

## 2. 当前结论

多项目切换不应通过“页面里临时改变量”实现，而应固定为三层切换：

1. 仓库级切换
2. 站点级切换
3. 页面级切换

## 3. 三层切换模型

### 3.1 仓库级切换

用途：

- 区分不同项目主仓库
- 区分主仓库与 legacy 仓库

当前示例：

- 主仓库：
  - `/Users/billchow/Documents/智慧冷冻站`
- legacy 仓库：
  - `/Users/billchow/Documents/chiller-station-legacy`

治理原则：

- 一个主控线程只维护一个主仓库
- 不在同一条开发/维护线程里混多个项目主语境
- 不把 A 项目的签收状态、字段口径直接搬到 B 项目

### 3.2 站点级切换

用途：

- 区分同一主仓库下的不同冷站站点

当前已有基础：

- `siteId`
- BFF 路径统一为：
  - `/bff/v1/sites/{siteId}/...`

治理原则：

- 站点切换必须统一落在 `siteId`
- 不允许在页面内部硬编码站点名当作切换方式
- runtime 配置、BFF route、页面深链接要共用同一站点标识

推荐承载位置：

- `runtimeConfig`
- URL query
- 路由 path 参数

当前仓库已落地的最小实现：

- 治理态项目选择页：`/projects`
- 页面 URL 当前统一追加 `?siteId=...`，用于表达当前站点主语义
- 当前项目选择仍会同步写入本地 session / localStorage，用于刷新后恢复当前项目
- BFF 继续沿用：
  - 路径 `siteId`
  - header `x-chiller-project-key`

当前口径：

- `siteId` 已进入页面 URL
- 但这仍是“单主仓库内的治理态项目切换”，不是 Phase 2 的多站点平台化
- 不应把当前 `/projects` 入口误读成“多项目统一工作台”已立项

### 3.3 页面级切换

用途：

- 区分同一站点下的业务面

当前已形成的稳定页面面：

- `/login`
- `/projects`
- `/dashboard`
- `/alarms`
- `/devices`
- `/system-overview`
- `/scene-control`
- `/trend-analysis`
- `/optimize-demo`

治理原则：

- 页面切换只解决“看哪一页”
- `/projects` 只承担“选择当前项目并回跳目标页”的治理态职责
- 其他业务页不承担“切项目”职责，只消费当前 `siteId`
- 页面状态必须跟随 URL 可回放

## 4. 当前阶段最稳的做法

### 4.1 多项目管理

如果并行维护多个项目，建议：

1. 一个项目一套治理文档
   - `ARCHITECTURE_CURRENT.md`
   - `FIELD_MAPPING_CURRENT.md`
   - `API_SURFACE_CURRENT.md`
   - `THREAD_RULES_CURRENT.md`
2. 一个项目一个主账本
   - 如 `v19.2-master-status.md`
3. 一个项目一个主控线程
4. 不跨项目共用运行结论

### 4.2 多站点管理

如果同一仓库未来接多个站点，建议：

1. 统一用 `siteId` 做站点主键
2. 页面、BFF、legacy adapter 都只认同一套 `siteId`
3. 页面 URL 应可直接表达当前站点
4. 签收、演示、回归结论按站点分别记录

## 5. 当前不建议做的事

在当前稳定维护阶段，不建议马上启动：

- 多项目统一工作台
- 跨项目共用前端壳重构
- 跨项目统一 BFF 平台重构
- 将当前 `/projects` 升格为多站点统一工作台
- 把当前单站点主仓库强行改成 SaaS 平台架构

原因：

- 当前项目已进入稳定维护阶段
- 现在做多项目平台化，会把项目重新拉回扩项状态

## 6. 如果后续真的要做多站点切换

最早触发条件应是：

1. 当前稳定维护阶段明确结束
2. 当前稳定维护阶段结束
3. 明确有第二个站点要接入同一主仓库

如后续明确启动 Phase 2，再进入评审：

- 是否加站点切换入口
- `siteId` 如何写回 URL
- 是否需要站点配置表
- 是否需要每站点独立 runtime profile

## 7. 当前动作建议

### 7.1 当前事项归类

- 类型：治理文档更新项

### 7.2 当前动作

- `maintain`

### 7.3 当前主控结论

当前应保持：

- 单主仓库治理
- 单站点主运行态
- 多页面稳定维护

而不是进入：

- 多项目平台化开发
- 多站点正式切换开发

## 8. 一句话结论

多项目切换现在先按“仓库 / siteId / 页面”三层治理，不做平台化开发；当前即使趋势页已签收，也仍需先完成一期维护态封版并获得明确批准，才进入多站点 Phase 2。
